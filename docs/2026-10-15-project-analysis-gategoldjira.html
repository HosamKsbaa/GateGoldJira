Section 1 · Context & Foundations

Background: Why Issue Trackers Are Deceptively Hard

At first glance, an issue tracker looks like a textbook CRUD application: users create tickets, assign them to teammates, and drag cards across columns on a Kanban board. Yet as soon as an organization scales to hundreds of concurrent engineers, automated CI/CD integrations, and AI coding assistants all mutating the same project simultaneously, naive CRUD architectures collapse under four subtle failure modes:

  • Lost Updates & Stale Overwrites: Alice edits an issue's priority while Bob updates its due date. If the client sends a full-record PUT, whoever clicks save second silently erases the other's change.
  • Workflow & WIP Race Conditions: A column has a hard Work-In-Progress (WIP) limit of 5 cards, and currently holds 4. Two engineers simultaneously drag different cards into that column. Under PostgreSQL's default READ COMMITTED isolation, both transactions see count = 4, both succeed, and the column ends up with 6 cards—violating the invariant.
  • Phantom Duplicate Mutations: A mobile or browser client submits a "Create Issue" or "Add Comment" request over an unstable connection. The server commits the transaction, but the HTTP response drops. When the client retries, a naive API creates a duplicate ticket.
  • Cross-Transport Drift: Modern engineering teams interact with work items through both a web UI (REST) and AI assistants (Model Context Protocol / MCP). When REST handlers and MCP tools contain separate validation or SQL logic, security boundaries and workflow rules inevitably diverge.
Deep Background Primer (Skip if familiar with MVCC, Advisory Locks, and Expand/Contract Migrations)

1. Snapshot Isolation (MVCC) vs. Write Skew

PostgreSQL uses Multi-Version Concurrency Control (MVCC). Readers never block writers, and writers never block readers. However, when a business rule depends on a predicate across multiple rows (such as "the total number of active cards in stage X must not exceed 5" or "adding edge A → B must not create a cycle in the dependency graph"), simply locking the single row being updated is insufficient. Two concurrent transactions can read the same snapshot, validate the multi-row invariant, and write disjoint rows that together break the invariant—an anomaly known as write skew. Preventing write skew requires either explicit lock coordination (such as PostgreSQL transaction-scoped advisory locks, pg_advisory_xact_lock) or REPEATABLE READ / SERIALIZABLE retry loops.

2. Idempotency Keys & Deterministic Command Receipts

To make network retries safe, mutations attach a client-generated UUID (an Idempotency-Key) along with a cryptographic hash (SHA-256) of the request payload. Inside the same database transaction that modifies domain tables, the server writes a row to a command_receipts table. If the client retries with the same key and payload hash, the server short-circuits execution and replays the stored JSON response. If the client reuses the same key with a different payload hash, the server rejects it with 409 Conflict.

3. Expand → Bridge → Backfill → Switch → Retire

When refactoring a live database schema (for example, replacing hardcoded status strings like 'in_progress' with foreign keys to a customizable workflow_stages table), dropping and recreating columns breaks running code. Instead, production systems use a 5-step choreography: (1) Expand new normalized tables alongside old ones; (2) Bridge writes via SQL triggers so old and new columns stay synchronized; (3) Backfill historical rows in bounded batches; (4) Switch application readers and writers to the new schema; and (5) Retire the old physical tables—optionally leaving behind updatable SQL views (INSTEAD OF triggers) so legacy API consumers continue working without data duplication.

Section 2 · Mental Models & Design Essence

Core Architectural Intuition

To understand GateGoldJira deeply, you only need four mental models. Almost every file in backend/ and frontend/ is a direct consequence of these four design choices.

2.1 Mental Model 1: One Domain Engine, Two Equal Citizens (REST & MCP)

In many applications, AI assistant support (MCP) is bolted on as a secondary wrapper that makes HTTP calls back to the REST API or duplicates SQL queries. GateGoldJira rejects both approaches. Instead, every domain package in backend/internal/features/<feature>/ exposes a transport-agnostic Service struct, flanked by two thin adapter files: http.go (Huma v2 REST routes) and mcp.go (MCP JSON-RPC 2.0 tool definitions).

Figure 1: Both Huma v2 REST and MCP Streamable HTTP adapters normalize inputs into the same command.Runner pipeline. However, JWT audience claims (/api vs /mcp) and command receipts (transport = 'rest' | 'mcp') remain strictly isolated.

Look at what happens when an engineer patches an issue's priority via the Angular web UI versus when Claude/Cursor invokes the issues_patch_modern_field MCP tool with toy data for issue GATE-42:

Both adapters strip transport wrappers, merge path and body parameters into a canonical JSON map, compute the identical SHA-256 payload hash, and call issueService.PatchModernField(...). Yet because command_receipts keys on (actor_user_id, transport, operation_id, idempotency_key), an MCP client can never replay or collide with a REST client's receipt, and a REST Bearer token is cryptographically rejected by the /mcp verifier due to audience mismatch.

2.2 Mental Model 2: Zero-Copy Compatibility via Updatable SQL Views (00018)

During the transition from V1 (where issues.status was a string like 'in_progress' and issues.priority was 'high') to V2 (where issue_records stores UUID foreign keys stage_id, priority_id, type_id, and workflow_id), how do you keep all 100+ legacy v1 REST/MCP operations working without maintaining two synchronized tables forever?

In migration 00018_retire_legacy_core.sql, GateGoldJira renamed the physical V2 tables to issue_records, board_records, assignment_rule_records, and attachments, and replaced the old table names (issues, boards, pictures, project_status_order, project_assignment_rules) with 14 updatable SQL compatibility views backed by PL/pgSQL INSTEAD OF INSERT OR UPDATE OR DELETE triggers: 

-- Simplified intuition of migration 00018_retire_legacy_core.sql:
-- 1. Legacy sqlc query runs: SELECT id, status, priority FROM issues WHERE project_id = $1;
-- 2. The `issues` VIEW joins `issue_records` with `workflow_stages` and `priority_definitions`
--    to project the legacy string columns (`status`, `priority`, `issue_type`) on the fly!
-- 3. When a legacy v1 endpoint runs: UPDATE issues SET status = 'done' WHERE id = $1;
--    The `write_issue_contract()` INSTEAD OF trigger intercepts the write, resolves 'done'
--    to the canonical `stage_id` UUID in `workflow_stages`, and updates `issue_records`!
Architectural Trade-Off: Why Refuse Lossy Legacy Writes in Modern Mode?

Once a project administrator activates Modern Mode (projects.core_mode = 'modern') and configures custom workflow stages or grouped board columns that cannot be represented in the 4-stage legacy vocabulary (todo, in_progress, code_review, done), legacy v1 write endpoints do not guess or silently coerce values. Instead, requireLegacyProjectMode returns an explicit upgrade error guiding the caller to the v2 identifier-based contract. Data integrity always wins over lossy backward compatibility.

2.3 Mental Model 3: The 6-Level Lock Hierarchy & Shared vs. Exclusive Lifecycle

In Epoch 1, every mutation on a project acquired an exclusive PostgreSQL advisory lock on the project UUID. That guaranteed zero deadlocks and trivial serializability—but under a 100-concurrent-user load test, 99 engineers editing issue descriptions or toggling priorities queued behind one another on the project lock.

In Epoch 2 (backend/internal/platform/command/locks.go), GateGoldJira introduced a Two-Tier Project Lifecycle Lock combined with a strict 6-Level Lock Acquisition Hierarchy:

Lock Mode PostgreSQL Primitive Who Uses It Concurrency Behavior
Shared Lifecycle
(SharedMetadata: true)		 pg_advisory_xact_lock_shared(class=1, key=fnv64a(project_id)) + targeted SELECT ... FOR UPDATE on the single issue/board row Whitelisted high-frequency operations: PatchIssueField, PatchModernIssueField, ReorderBoardCard, SaveCustomFields, VoteApproval, ResubmitApproval 100+ concurrent writers run in parallel across different issues in the same project, while preventing project archival/deletion or workflow schema changes underneath them.
Exclusive Lifecycle
(ExclusiveLifecycle: true)		 pg_advisory_xact_lock(class=1, key=fnv64a(project_id)) Structural mutations: workflow/stage edits, stage retirement, modern-mode activation, dependency graph mutations, stage transitions affecting hard WIP Drains active shared metadata writers, executes the structural change atomically against a stable project snapshot, and releases on commit.

To guarantee that concurrent transactions acquiring multiple locks can never deadlock, command.AcquireLocks sorts all lock requests deterministically by a 6-level hierarchy before issuing a single SQL lock statement: 

Level 1: ProjectLifecycle  (class 1)  — Shared or Exclusive per-project barrier
Level 2: Configuration     (class 2)  — Workflow / taxonomy / field definition changes
Level 3: BoardLayout       (class 3)  — Board columns, stage mappings, and WIP settings
Level 4: IssueGraph        (class 4)  — Dependency & subtask DAG cycle checks
Level 5: BoardOrder        (class 5)  — Per-board lexicographical/integer card ranking
Level 6: IssueRow          (class 6)  — Individual issue row mutations (sorted by UUID)

2.4 Mental Model 4: How Migration 00019 Solved the 200k-Issue Board Bottleneck

During the 200,000-issue / 100-concurrent-user scale verification (modern-completion-performance.md), board loading p95 latency initially spiked to ~630 ms—exceeding the 500 ms SLA budget.

Profiling with EXPLAIN (ANALYZE, BUFFERS) revealed a classic database insight: fetching the first 50 cards per column via keyset pagination was fast, but computing exact total card counts per column across 200,000 issues was scanning tens of thousands of heap pages. Worse, if a board mapped two workflow stages to the same column, naive joins double-counted or spilled to disk.

The Migration 00019 Fix: Index-Only Partial Stage Counting (630 ms → 405 ms)

Instead of adding denormalized counter columns (which would turn every issue transition into a hot-row lock bottleneck!), migration 00019_active_stage_count.sql added a compact partial B-tree index on issue_records (project_id, stage_id) WHERE archived_at IS NULL AND backlog_Entered_at IS NULL, paired with a deduplicated stage-array query (CountProjectIssuesByStages). PostgreSQL satisfies exact column totals via pure Index-Only Scans in a single REPEATABLE READ snapshot, dropping 200k-issue board p95 latency from 630 ms down to 405.00 ms with zero write amplification.

3.2 Inside the 11-Phase Transactional Command Pipeline

Every state-changing operation across all 12 features executes through command.Execute / Runner.ExecuteWithAccess. Here is the exact 11-phase lifecycle of a mutation:

Phase 1 – 2

Envelope & SHA-256 Digest

Validates Actor.UserID, Operation (1 of 134 typed IDs), and IdempotencyKey. Computes canonical transport-neutral SHA-256 hash of the request payload.

Phase 3 – 4

Tx Open & Lock Ordering

Opens a pgx.Tx (ReadCommitted or RepeatableRead) and acquires sorted advisory locks (SharedMetadata or ExclusiveLifecycle).

Phase 5 – 6

Pre-Replay Auth & Receipt Check

Runs Authorize(ctx, queries) before checking command_receipts so a revoked user cannot replay cached responses. Replays stored JSON on hash match.

Phase 7 – 8

Domain Work & GuardWIP

Executes the feature's mutation closure, then invokes Runner.WriteGuard (boards.GuardWIP) to verify no hard-capped board column exceeded its WIP limit.

Phase 9 – 11

Audit, Outbox & Commit

Appends immutable activity_events, enqueues deduplicated notification_events, persists the command_receipts row, and commits (retrying 40001 up to 4×).

3.3 64-Bit Midpoint Ranking, Rebalancing & Lazy Unranked Tails

Kanban boards and backlogs require arbitrary drag-and-drop reordering without renumbering thousands of rows on every move. GateGoldJira implements a hybrid 64-bit integer gap ranking + lazy unranked tail algorithm in issues/order.go and boards/movement.go:

  • Midpoint Bisection (RankGap = 1024): Adjacent ranked cards are spaced by 1024. Inserting a card between rank $A$ and rank $B$ assigns $\lfloor(A + B) / 2\rfloor$ in $O(1)$ time (RankBetween), supporting $\log_2(1024) = 10$ consecutive insertions into the exact same slot before gap exhaustion.
  • Bounded Rebalancing (MaximumRebalance = 2000): When $B - A \le 1$, RebalanceRanks re-spaces the active ranked prefix in multiples of 1024, capped at 2,000 items so rebalancing never causes unbounded transaction latency.
  • Lazy Unranked Tails: In a 200,000-issue project, pre-populating board_issue_ranks for every board would multiply storage and write costs. Instead, newly created issues have no row in board_issue_ranks until explicitly dragged! Board queries (boards/reads.go) read Phase 1 (explicitly ranked cards ordered by rank ASC) followed seamlessly by Phase 2 (unranked cards ordered by issue_number ASC), encoded into an HMAC-SHA256 signed cursor (Section: "ranked" | "unranked").

3.4 Lock-Free Two-Phase Private Media Storage

Holding a PostgreSQL transaction open while streaming a 10 MiB file to Google Cloud Storage would exhaust the database connection pool and stall advisory locks. GateGoldJira's media pipeline (features/attachments/ and platform/objectstore/) strictly separates network I/O from database transactions:

  1. Concurrency Gate: Middleware (objectstore.TransferGate) limits each backend instance to at most 2 concurrent binary transfers, returning 429 Too Many Requests if saturated.
  2. Phase 1 — Session & Chunked Staging (Outside Domain Locks): The client creates an upload_reservations row and uploads chunks (`256 KiB`–`8 MiB`) to the private Staging Bucket. Magic-byte sniffing (validation.go) verifies PNG/JPEG/WebP/PDF/CSV/Office headers and explicitly blocks SVG/HTML/executable script payloads.
  3. Phase 2 — Content Promotion & Reference Binding: When the issue description or comment is saved, PrepareAssets copies verified staging objects to the immutable Published Bucket (where the runtime IAM service account has no delete permission) and records SHA-256 + GCS generation numbers before opening the short SQL transaction that binds issue_asset_references.

3.5 Contextual 5-Tuple Approvals & Cross-Command GuardWIP

Two pieces of domain logic in issues and boards stand out for their rigor:

  • 5-Tuple Contextual Approvals (canonical_transitions.go): When a workflow transition requires approval, an approval vote in issue_approvals is cryptographically bound to the 5-tuple (issue_id, transition_id, issue_revision, workflow_revision, configuration_revision). If someone modifies the issue's content, edits the workflow graph, or alters project configuration after an approver votes "Approved" but before the transition executes, the revision tuple no longer matches and the stale approval is automatically invalidated!
  • Cross-Command Hard WIP Enforcement (boards/wip.go): A board column can configure a hard WIP maximum. Because cards can enter a stage not only via board drag-and-drop, but also via issue creation, bulk stage edits, backlog promotion, CSV import, or stage retirement, boards.GuardWIP is wired into Runner.WriteGuard and inspects all 18 occupancy-changing operations before transaction commit. Furthermore, to ensure WIP counts are deterministic for all users, hard-capped boards prohibit viewer-relative or time-relative saved search filters (such as AssigneeMe or Overdue).

3.6 Angular 22.2.2 Signal State, sessionEpoch & Deterministic Retries

The Angular frontend (frontend/src/app/) uses standalone components with ChangeDetectionStrategy.OnPush and native Angular Signals (signal, computed, effect), backed by three resilience primitives in src/app/core/:

  • AuthService.sessionEpoch (auth.service.ts): A monotonically increasing counter incremented on sign-out or 401/403 responses. Every in-flight RequestState captures the epoch before awaiting a promise and discards late responses if the epoch changed—preventing stale data from a previous user or project from polluting the UI.
  • RetryIntent (retry-intent.ts): Memoizes a generated UUIDv4 Idempotency-Key per (operationKey, JSON.stringify(payload)). If a save fails due to a transient network drop and the user clicks "Retry" without changing the form, the exact same Idempotency-Key is sent; if the user edits a field, a fresh UUIDv4 is generated automatically.
  • DraftsService (drafts.service.ts): Persists unsaved edits and multi-step issue creation state (createdIssueId + resumable attachment upload session IDs) in sessionStorage, guarded by draftGuard on route navigation.
