# Managed identity deployment candidate

GateGoldJira uses Auth0 for Google login and delegated MCP authorization. This directory contains a typed **candidate**, not a provisioned tenant. The owner chose local development on 2026-10-12; tenant, workforce licensing, actual Google sign-in and selected assistant compatibility remain pending.

## Configuration

1. Review `tenant.example.json` with the tenant owner. Replace public issuer, audiences, origins and client IDs. Register distinct RS256 APIs whose identifiers exactly match the Go REST audience and `/mcp` resource. Give approved public clients only `gategoldjira:access`; company approval and roles remain in PostgreSQL.
2. Register Angular as a public SPA using authorization code with S256 PKCE, exact callback/logout URLs and web origins. The browser uses memory tokens. Create the MCP reference application as a public native client, `token_endpoint_auth_method=none`, with its exact callback. No client secret or machine grant is used. Auth0 documents S256 and resource/audience behavior in its [PKCE authorization reference](https://auth0.com/docs/api/authentication/authorization-code-flow-with-pkce/authorize-with-pkce).
3. Enable the tenant's Resource Parameter Compatibility Profile. The MCP SDK sends `resource` in authorization and token requests; it must resolve to the registered MCP API. Verify this rather than accepting a userinfo/REST token. Keep DCR disabled. For a selected CIMD assistant, review its HTTPS metadata and import it manually in Auth0, register exact callbacks and grant only this API. Record the resulting public configuration. These options are documented in [Tenant Settings](https://auth0.com/docs/get-started/tenant-settings).
4. Configure Google OAuth credentials in the managed Google connection and enable it for the approved clients. Keep Google's credential secret with Auth0. Build `dist/actions/verified-email-action.cjs` with `npm run build`, upload its compiled Action, attach it to Post Login and test it. The Action accepts `google-oauth2` and adds verified namespaced email claims. It rejects other strategies. A later Google Workspace enterprise connection needs a reviewed Action/entitlement change. Follow [Auth0's Google connection setup](https://auth0.com/docs/authenticate/identity-providers/social-identity-providers/google).
5. Before external launch, record workforce/internal-employee eligibility, active-user pricing, region, connection/client feature entitlements and selected assistant/version/registration method. Manually registered third-party/CIMD clients need an explicit API grant; confirm their consent and supported configuration using [third-party security controls](https://auth0.com/docs/get-started/applications/third-party-applications/security-controls). Do not enable open DCR merely to avoid registering one client.

## Approving and onboarding employees

An Administrator approves the employee's exact verified Google email on the Company users page, then grants the appropriate project membership. Share the workspace URL with the employee; they sign in through the configured Google connection using that same account. Approval is separate from project access. The application approval form does not send invitation email or set a Google password. Authentication claims bind to the approved account on its first valid login.

Local development uses only its existing private fixture usernames and passwords. Approving an email does not create another local credential. Keep those fixture credentials out of employee onboarding; real Google login begins after the tenant configuration above has been completed and verified.

## Local MCP browser OAuth

The local development app supports browser authorization using existing GateGoldJira usernames/passwords. The loopback adapter is registered only for explicit development auth with local storage and loopback database, issuer, API and browser origins. Production keeps the managed issuer for browser sign-in. Setting `MCP_BROWSER_OAUTH_ENABLED=true` additionally enables GateGoldJira’s HTTPS MCP OAuth broker: browser consent uses the verified OIDC account, while the MCP client receives its own revocable opaque credential. The broker advertises the canonical API `/oauth` issuer. No local password login endpoint or fixture key is enabled in production. The native Antigravity plugin uses this broker; the default remains direct managed-provider discovery unless explicitly enabled.

Antigravity's public client ID is `gategoldjira-antigravity`. The MCP resource advertises the reachable local issuer at `http://localhost:21080/oauth`. OAuth discovery is `/.well-known/oauth-authorization-server/oauth`. The client uses authorization code with mandatory S256 PKCE and `resource` binding, then rotates refresh credentials. Access credentials last 15 minutes, refresh credentials have an absolute 30-day lifetime, and every connection can be revoked immediately. Protocol state and only credential hashes persist in PostgreSQL, so restarts preserve access. The browser requires an explicit signed-in approval; denial issues no credential. Refresh reuse revokes the associated connection.

Run `scripts/setup-antigravity-mcp.sh` against the running local server after migrations through 22. It verifies OAuth discovery, saves private backups, preserves unrelated servers and configures a pinned `mcp-remote@0.15.1` stdio proxy. The configuration includes the pre-registered public client ID, exact resource, scope and IP loopback callback host. Install Node.js 22 or newer, reload the server in Antigravity, then sign in and approve the browser connection. If no browser opens, use the authorization URL in the MCP server logs. No Authenticate button is required. The IDE callback is `https://antigravity.google/oauth-callback`; native public clients may use an IP loopback callback with an explicit port at `/oauth/callback` or `/callback`. Redirects to other hosts/paths are rejected.

Open `/account/mcp-tokens` to copy OAuth configuration, view connected clients, inspect activity or revoke access. Personal tokens remain an explicit fallback. OAuth connections share the same per-connection activity history without recording secrets or file content. Revocation blocks access and refresh on the next request.

## Personal MCP tokens

Every signed-in, active approved user can open **Account MCP tokens** in the application header, or `/account/mcp-tokens`, to create their own named credentials. Tokens never expire and remain valid until revoked. Existing active personal tokens become permanent when migration 21 runs; expired or revoked tokens stay invalid. Each account can have up to 10 active tokens. The full token appears only in the creation response and is held in page memory until dismissed, navigated away or signed out. The database stores its SHA-256 hash, a short identifying prefix and lifecycle metadata; neither retry receipts nor logs store the credential.

Use **Copy Antigravity config** to copy the server URL and `Authorization: Bearer <token>` header. Merge that entry into Antigravity's MCP configuration and refresh its servers. These credentials work with the existing local sign-in accounts without provisioning Auth0. They also work for approved accounts authenticated through the production browser identity provider once it is configured.

The authenticated REST-only endpoints are `GET /api/v1/me/mcp-tokens`, `POST /api/v1/me/mcp-tokens` with `{name}`, and `POST /api/v1/me/mcp-tokens/{tokenId}/revoke`. No assistant tool can create credentials. A personal MCP token authenticates only `/mcp`, cannot access the REST API, and always resolves to its existing owning user. Current approval, disabled status and project permissions apply on each request; revocation rejects the next request. Token lists expose metadata only and never other users' credentials, including to administrators.

Apply migrations through 21 before starting the updated API. Reapply `infra/sql/runtime-grants.sql` for restricted production runtime roles. OAuth access tokens remain supported alongside personal tokens. The one-hour development-token setup script is still a fixture helper; account-created tokens do not require it.

Each token has an owner-only activity history at `GET /api/v1/me/mcp-tokens/{tokenId}/activity`, with optional `before` UUID pagination (25 calls per page). The account page offers **View activity** for active and revoked tokens. It records registered tool calls, times, outcomes, stable error codes and returned resource links. Arguments, uploaded bytes, credentials and response bodies are never recorded. A durable attempt is written before execution; if completion cannot be recorded, the history shows completion unconfirmed. History starts when this feature is installed.

## Compatibility evidence to collect

Use the pinned Go SDK 1.8.0 reference client in `backend/tests/mcp/client.go`, plus the chosen actual assistant. Record issuer/AS discovery URLs, public client IDs, exact callbacks, resource, scope and negotiated protocol (2025-11-25 and 2026-07-28 are supported). Verify S256/state/issuer checks, token audience/expiry, human attribution, REST/MCP wrong-audience rejection and next-call account/project revocation. Check discovery endpoints with and without the issuer trailing slash: the pinned SDK requests a trailing-slash metadata URL for a root issuer.

Do not record codes, verifiers, access/refresh tokens, cookies or Google/provider secrets in reports. Keep business snapshots/event IDs and redacted status results. Test across independent backend instances and restart. Complete all provider/assistant cases in T133/T135 after the remaining stories are built.

`backend/tests/mcp/fixture_test.go` supplies a test-only issuer to exercise real SDK discovery, one-use codes, exact redirects, S256 and signed human tokens against isolated PostgreSQL. It also exercises public-client authentication negotiation: Basic is rejected without consuming a code, then the SDK retries with the public client ID in the form. The application never exposes that issuer or custom authorization/token routes. Passing this fixture does not prove Auth0 tenant compatibility.

See `docs/mcp-onboarding.md` for distributing configuration to other users. Do not assume every MCP host supports remote Authorization headers; verify the chosen host/version. The proxy provides a stdio alternative.
