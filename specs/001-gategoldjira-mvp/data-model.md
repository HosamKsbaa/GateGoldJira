# Data Model: GateGoldJira Full MVP

**Date**: 2026-10-11 | **Authority**: [spec.md](spec.md), [constitution](../../.specify/memory/constitution.md)
**Status**: Baseline schema and the dated addenda below are implemented as ordered additive migrations. Isolated PostgreSQL tests verify schema, retained history and service invariants; final acceptance evidence is recorded under validation/.

## Conventions and types

PostgreSQL 18; versioned goose SQL migrations; all queries generated by sqlc for pgx/v5. Domain IDs are distinct Go UUID wrappers, using server-generated UUIDs. Database timestamps are timestamptz/UTC; JSON timestamps are RFC3339 UTC. Revisions and issue numbers are positive bigint internally and decimal strings on the wire to preserve JavaScript precision. Counts are bounded integers. Due dates use PostgreSQL DATE and a validated Go calendar-date type, represented as YYYY-MM-DD without browser Date conversion.

Use explicit Go enums and database checks for role, status, type, priority and notification reason. API enums: member/viewer; todo/in_progress/review/done; task/bug/subtask; low/medium/high. All string length checks count Unicode characters, with separate byte limits for HTML and files. Preserve Arabic text; normalize only keys/email and case-insensitive uniqueness lookup keys. Labels/board names use trimmed display values plus a consistently derived Unicode case-folded uniqueness key, without discarding the original text.

Company calendar is Africa/Cairo from validated configuration persisted in company_settings. No timezone-settings UI is introduced. No permanently deleted business entities. JSONB is confined to versioned typed board filters, audit changes and retry result envelopes; sqlc outputs are decoded into concrete structs at the repository boundary.

## State transitions and derived values

- Account: Admin approval -> active; active <-> disabled; Admin grant/revoke preserving memberships. Each global change checks last-Admin protection and clears newly ineligible current assignments across affected projects in the same transaction. Restore does not reassign old work.
- Project: active <-> archived by Admin. Archived reads and membership administration allowed; project content and board-mediated moves denied.
- Board: custom active <-> archived by eligible creator/Admin; default always active/all issues. Settings change board revision only, not issue content.
- Issue workflow: four initial stages plus project-registered custom stages; each board defines allowed moves. A completed-category stage requires zero unfinished direct blockers and, for a parent, zero unfinished children. A subtask cannot reopen while its parent is Done; creation requires a non-Done Task/Bug parent. Review has no extra role/approval rule. Task/Bug conversion allowed; Subtask conversion/nesting/reparenting denied.
- Dependency: absent/removed -> active -> removed, under graph checks. Duplicate active add returns existing relationship. An unfinished blocker cannot be added to a Done dependent. Reopening a blocker may mark a Done dependent blocked without reopening it; a child still requires its Done parent reopened first.
- Picture: complete private draft -> published only on successful gallery publication or comment save. A draft becomes unavailable at expires_at; maintenance removes unreferenced expired/orphan objects. Published and prior-version images never expire.
- Notification: unread <-> read by recipient; opening an inbox entry performs an explicit read-state mutation. Mark-all affects currently accessible entries at the transaction snapshot, not inaccessible entries or future events. No notification generated by read-state changes.

Derived blocked = EXISTS(active direct blocker with status != done); unfinished count is direct only. Overdue = due_date < company_today AND status != done; today/undated are false. Parent progress = done_child_count / total_child_count. WIP counts include all parents/subtasks matching the saved board view in a status; warn only count > nullable limit. Temporary filters change visibleMatchCount and cards but never savedMatchCount/WIP. Compute company_today once per request/transaction so responses agree at midnight.

## Transaction, conflict and retry protocol

1. Verify JWT and derive actor from the transport. Start a short READ COMMITTED transaction; acquire company_settings row FOR SHARE for ordinary mutations, FOR UPDATE for global account/Admin/binding changes. Recheck approved/active caller and operation permission.
2. Claim (actor,retryReference) before project locks or business changes. Compare a deterministic hash of operation and canonical service arguments, including expected revisions but excluding transport/channel. A committed matching retry rechecks current operation/resource authorization before returning the saved result; never revalidate stale expected revisions on a replay. A mismatching key returns retry_reference_reused. Concurrent duplicates wait briefly on the unique claim, then return original result or a retryable busy outcome.
3. Lock affected project rows FOR UPDATE in sorted UUID order. Ordinary content, membership, archival, ranking and graph commands all use this ordering. Global account changes hold the exclusive company guard then acquire affected projects in sorted order; no command upgrades a shared guard mid-transaction.
4. Check project active state, current ownership/assignee/mention eligibility, entity expectedRevision, graphRevision for explicit link changes, and source/target order revisions for card moves. Create does not require an entity revision; membership initial creation requires revision 0. A stale command rolls back and returns only current authorized state. Derived graph/order revisions are independent from editable project revision.
5. Apply canonical service changes; append immutable comment versions where applicable. Increment only relevant entity/graph/order revisions. Allocate an issue number using an atomic project counter update; never reuse identifiers. Collect one mutation event and its affected-issue changes.
6. Insert audit records, assignment cleanup, and the exact deduplicated notification set in the same transaction. For each affected issue union eligible reporter/assignee/new mentions under spec rules, exclude actor, combine reasons, insert unique event+issue+recipient. Compute blocked/unblocked and last-child-Done transitions from before/after state, including indirect affected dependents/parents.
7. Store the typed result/retry record and commit. Publish success only after commit. A timeout after possible commit instructs reuse of the same retry reference. Do not retry arbitrary business conflicts silently; user reviews current state and sends a new intention/reference.

No object/network transfer occurs while holding project locks. Upload reservation and checksum validation happen before the final short permission-checked commit. Before publishing, copy/verify an immutable published object under a reserved ID using generation preconditions; failed DB commit leaves an inaccessible orphan for maintenance. The final transaction rechecks current authorization/expiry and references only a confirmed object generation. No cleanup may delete a live reservation or a referenced/published object. Use separate staging/published buckets; ordinary runtime can create/read published objects but cannot delete them; maintenance identity may remove verified staging/uncommitted orphans only. Absence of a SQL reference alone is never proof of an uncommitted published-bucket orphan; require a confirmed failed reservation and matching generation. Suspend cleanup during restore until reservation/object metadata is reconciled, and retain uncertain published objects.

Personal read-state transactions use the shared company guard and short shared project locks in sorted order to serialize against membership revocation, then recipient notification rows in sorted ID order. Multiple inbox changes can share the project guard; they still wait for a conflicting content or membership write. Account/membership revocation completed before a new action is visible to that action. Reads authorize at the same SQL snapshot as returned data; counts use identical predicates. No cached permission claims or sticky sessions.

## Completion graph and shared rank algorithm

Edges point from work to its prerequisite: dependent -> explicit blocker and parent -> each subtask. Adding A->B rejects when B reaches A across either kind, using a recursive CTE with a visited path. Creating a child and all status/link changes hold the project write lock; this protects cycle checks and parent/child completion concurrently. It is an intentional simple MVP tradeoff, measured under the full 50-user load.

Rank is a bigint per project/status, initially spaced by 1024. Append after last rank; insert before/after a referenced issue using a gap midpoint under the same project lock. If no gap or overflow risk, rebalance the bounded project/status list to spaced ranks in one transaction, retaining every other issue's relative order. Rank changes do not masquerade as content edits to other cards. Tie-break by permanent issue identifier. Both source/target order revisions are required for status moves; within-column reorder uses one revision. A filtered board sends IDs of the moved card and real neighbor, never its partial client array as the whole order.

## Query plan, pagination and indexes

Keyset pagination, default 25/max 100, with signed/versioned opaque cursors binding operation, actor, normalized filter/sort and last tuple. No cursor carries authorization. Validate signatures/filter bindings and recheck permissions on every page. For unchanged datasets each sort has a unique final identifier; if ordering/filter membership changes, clients may refresh, and rank cursors with changed order revisions return conflict rather than mixing order. No long-lived DB transaction across HTTP pages.

| Access pattern | Initial index / query approach |
| --- | --- |
| Project access | memberships(user_id,project_id) for nonremoved membership; explicit Admin predicate with active approved account |
| Ordinary issue lists / My Issues | (project_id,updated_at DESC,id DESC); partial (assignee_id,updated_at DESC,id DESC) |
| Board cards | (project_id,status,rank,number); permanent issue number is the stable identifier tie-break within one project |
| Exact key / title substring | unique(project_id,number); pg_trgm GIN(title) with ILIKE and permission/project predicates; measure very short searches |
| Children / dates / labels | (project_id,parent_id,id); (project_id,due_date,id), partial open due dates; issue_labels(project_id,label_id,issue_id) |
| Blockers and reverse affected dependents | active indexes (project_id,dependent_id,blocker_id) and (project_id,blocker_id,dependent_id) |
| Comments / versions / pictures | (issue_id,created_at,id); unique(comment_id,revision); (issue_id,uploaded_at,id) |
| Inbox / unread | (recipient_id,created_at DESC,id DESC); same partial WHERE read_at IS NULL, always joined to current project access |
| Company history / resource history | (created_at DESC,id DESC); (resource_kind,resource_id,created_at DESC,id DESC) |
| Expiry cleanup | drafts(expires_at); retry_records(expires_at); reservation lease_until |

Use shared typed filter compilation into parameterized sqlc queries; selected labels mean ALL, ranges inclusive/exclude null dates, not-overdue includes null, parent filter returns children only. No query from client-provided SQL. Aggregate blockers, children, assignees and labels with bounded batch queries/CTEs, not per-card queries. Board counts and first pages use one short REPEATABLE READ read-only snapshot; each count carries saved/visible distinction. Ordinary JSON pages additionally stop at a 1 MiB encoded-payload budget and may return fewer than the requested record count, with the cursor anchored at the last returned item. Picture bytes use their separate transfer budget. Query plans, lock waits, pool waits and memory are acceptance measurements, not assumed outcomes.

## Data verification and recovery

Use real PostgreSQL integration cases for every cross-row invariant: last Admin, role revocation/assignment clearing, project archival races, number uniqueness, equal retry claims/different-input reuse, dependency+parent cycles, parent Done versus child create/reopen, shared hidden-card order and transactional notification dedupe/privacy. Restore tests include all retained comment versions, prior pictures, audits and read state. Production recovery and expansion/rollback rules are in [plan.md](plan.md) and [quickstart.md](quickstart.md); no destructive migration is assumed for this new application.


`prerequisiteFor` is a read-only issue-search criterion over the union of active explicit blocker edges and direct children. It changes no stored relationship and lets bounded completion rejections continue through the existing search operation. Current project visibility applies to every returned row and count.

Explicit dependency add/remove/re-add advances the relationship revision and project graph revision; issue editable-field and column-order revisions remain unchanged. Completion-state changes also advance the graph version because unfinished-prerequisite and blocked filters change. Both entity and graph versions are still required to link work from a fresh issue view.

Admin activity reads use time/ID keysets and one consistent permission/count snapshot. Resource filters are a kind/ID pair. Issue and project filters include relevant assignment cleanup/reciprocal graph changes from other root resources. Personal read-state events expose attribution/resource/time and safe read-state metadata only. Public previews have a closed field vocabulary, at most50 changes and1024 Unicode characters per old/new value; an explicit abbreviation notice distinguishes the preview from full retained audit values. SQL bounds the projection before returning it to Go, and ordinary page construction enforces the1MiB envelope budget.

## Issue document attachments addendum (2026-10-12)

`attachments` stores immutable ID, issue/project/uploader attribution, filename, allowed MIME, 1–10MiB byte size, SHA-256, exact staging/published object generations and upload time. `attached` is the sole mutable metadata field. Detach hides the document from the issue list; retained metadata and private bytes remain accessible by ID to current authorized project readers. An index on `(issue_id,uploaded_at,id) WHERE attached` supports stable bounded cursor pages.

`attachment_upload_reservations` has a caller/retry primary key, canonical input hash including metadata and bytes checksum, attachment ID, immutable object keys/generations, a 45-second transfer lease and uploading/ready/failed/committed states. No database connection or project lock remains held during object I/O. Reservation finalization and metadata commit recheck current writer/project state. Upload and CAS detach advance issue revision and append an attachment activity event in the shared transaction; replays preserve result/event identity. Failure recovery reuses confirmed object generations and the original reference.

Migration `00004_attachments.sql` is additive and leaves the picture/comment pipeline untouched. Database triggers permit only attachment reference changes, retaining immutable history. Rollback must preserve stored files and metadata first; an older application can ignore the new tables. Published-object deletion remains unavailable. The existing maintenance job also processes up to 100 known failed attachment staging objects older than 24 hours under the shared restore-pause guard; generation uncertainty is retained for reconciliation.

## Daily workflow model (2026-10-13, supersedes per-board rules above)

Migration00006 adds `project_status_order.retired`. A workflow contains at least two stages with at least one unstarted and one completed category. Stable identities cannot be resurrected after retirement. An explicit workflow save synchronizes all project boards under the project lock, including names/order/allowed edges and per-stage optional `warningLimit` (0 disables; omitted uses the existing per-board category fallback). A retirement supplies a retained replacement, moves up to100 issues with normal completion/reopen/prerequisite checks, remaps exact-stage board filters, then hides the old registered stage; history and order identities remain. REST/MCP moves without a board still enforce the shared rules. Older per-board configurations remain conservatively enforced until an explicit save reconciles them.

Migration00007 adds `issues.archived` and `issues.backlog`, both default false. Backlog accepts unstarted work; a stage move removes it from backlog. Board counts/pages exclude archived/backlog items; normal issue search excludes archived items unless requested. No business rows are deleted. Search cursors bind sort/filter/actor and a stable sort value/update-time/ID tuple for updated, created, due and priority orderings.

`issue_watchers(issue_id,user_id)` stores private caller-owned subscription state, updated idempotently. Watcher recipients join current active account/project access at notification commit, exclude the actor and merge the new watching reason with existing reasons; uploading/detaching published files also notifies watchers. Unpublished comment picture drafts do not. Reader issue history excludes personal read-state and subscription events.

`issue_links(issue_id,target_id,kind)` stores same-project relates-to/duplicates with created attribution and retained removed_at. Relates-to canonicalizes endpoint order; duplicates retains direction. Both endpoints advance issue revision, so stale issue edits cannot overwrite a relation change. Up to100 active links per endpoint remain bounded. These links do not participate in completion/dependency graphs.

`saved_issue_searches` is private to its owning user, with validated filter JSON, permanent UUID, revision, removed flag, name uniqueness and a50active-search limit serialized under the user row lock. It is exposed through the same typed REST/MCP service. Ordinary runtime grants allow changes only to intended mutable columns and deny row deletion or ownership rewriting.

Browser drafts contain typed field snapshots, their original revision, selected File objects and retry references only in memory. They are scoped by issue/editor and cleared on sign-out/session invalidation. A partially created issue retains its ID so subsequent upload retries cannot duplicate creation. Bulk changes reuse existing single-issue commands and CAS checks; no extra bulk transaction service or queue is introduced. Attachment references remain ordinary same-origin links to private retained metadata; previews fetch authorized bytes and revoke temporary blob URLs when closed.

| planning_completion_cycles view | completion event, issue/project, completed_at, nullable started_at | Every transition from an unfinished category into Done is one episode. Find its first recorded In progress/Review entry since the previous completion, or its reopen event. A missing historical start remains null. |

Planning lists sort by kind/name under PostgreSQL C collation/ID; linked work and current aging work sort by permanent issue number. Pages use the shared 25-default/100-maximum signed actor/operation/filter-bound cursors and 1 MiB envelope budget. Indexes cover `(project_id,kind,name COLLATE "C",id)`, partial epic/release issue associations and issue transition history.

A report reads one repeatable-read authorized snapshot. Its inclusive UTC date window is 1–366 days. Throughput counts completed episodes by completion day, including repeat completion after reopening. The first In progress/Review entry starts a measured cycle; returning to To do keeps that start. Done→unfinished opens a new episode at the reopening event, even when reopening to To do. Initial active-category issue creation records a start; To do→Done without a start contributes to throughput but not the cycle average. The average is null when measured count is zero. Timing never derives from issue updated_at.

Current-work metrics are independent of the historical date window: they exclude archived/backlog/Done work, count current direct unfinished blockers, derive total age from creation and derive cycle age only from a recorded open episode. `snapshotAt` makes the observation time explicit. Every output count uses the same current permission/project scope as its records. No stored counter or imported timestamp invents earlier workflow activity.

Planning record events are project-resource events with record attribution and typed field changes. Association changes are issue-resource events identifying epic/release changes. Replay rechecks current permissions and returns the exact original receipt without another event. No-op replacements do not increase revisions or create events.

The application injects `ApplyStageRule` as a transaction-bound issue-service callback to preserve feature package boundaries. Initial active issue creation and stage movement call it after their ordinary workflow, completion and project checks. Pending backlog creation defers application until activation. The callback rechecks enabled rule, registered stage and current eligible assignee under the existing mutation/project lock. If eligible and different, it changes the assignment and issue revision, appends actor-attributed assignee changes, and emits the deduplicated assignment notification in the same transaction. Ineligible historical configuration is skipped. A rule never bypasses a blocker/subtask guard or starts a nested command. Command replay cannot create another automation event or notification.

These additions are additive. Production rollback preserves retained planning, assignment, link and rule rows, and uses a forward-compatible application release rather than dropping populated history.
